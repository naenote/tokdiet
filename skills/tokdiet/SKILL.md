# tokdiet

ローカルのログから、トークンの使い道を測り、改善案を証拠つきの計画にして出します。計画で止まります。承認前に、設定もスキルもコードも変更しません。

このファイルと同じ場所の `scripts/` に、実行するスクリプトがあります。以下の `<scripts>` は、このスキルのディレクトリの `scripts/` を指します。

## 手順

### 0. 実行前にスクリプトを読む
`<scripts>` の `tokdiet.py`、`actionbrief.py`、`leakcheck.py` を Read で読み、実行する前に次を確かめます。外部から入れたコードを、読まずに実行しないためです（約 2,000 行です）。

- 通信しない。他のコマンドを起動しない。
- 書くのは、`--out` の配下と、`--snapshot` で指定したファイルだけ。
- 読むのは、ログと、ログに記録された作業ディレクトリの git リポジトリ内のファイル、指示ファイル、スキル定義（README の「ログは外に出ません」の節のとおり）。

README の記述と違う点があれば、実行せずにユーザーに伝えます。

### 1. 測る
出力先はリポジトリとログの外にします（例: `~/tokdiet-out`）。

**単価を用意します。** このスキルは価格表を持ちません。単価はモデルごとに違うので、ログに出てくるモデルだけを調べます。

1. `python3 <scripts>/tokdiet.py --list-models` で、ログに出てくるモデル ID を一覧します（`--root` を使うときは同じものを付けます）。
2. `claude-api` スキルを呼び出して、そのモデル ID の API 単価（入力、出力、キャッシュ読み取り。単位は 100 万トークンあたりのドル）を読み取ります。
3. 次の形で `~/tokdiet-out/prices.json` に書きます。

```
{"<モデルID>": {"input": <数>, "output": <数>, "cache_read": <数>}}
```

- 値は `claude-api` スキルが示したものだけを使います。記憶や推測で埋めません。ログのモデル ID に日付が付いているとき（例: `claude-haiku-4-5-20251001`）は、日付を除いた ID（`claude-haiku-4-5`）がスキルの表にあれば、日付なしのキーで書きます（スクリプトは日付を除いて照合します）。スキルの表に載っていないモデル（古い世代など）は書かず、書けなかったモデルをユーザーに伝えます（そのモデルの金額は「単価不明」になります）。Opus や Sonnet という系列名だけで、別の世代の単価を流用しません。
- `cache_read` は、スキルが金額を示したモデルだけ書きます（示された倍率が 0.1 倍でないモデルがあります）。書かなければ入力単価の 0.1 倍で計算します。キャッシュの作成（1.25 倍、2 倍）はスクリプトが固定で計算します。
- スキルの価格表は「キャッシュした日付」付きです。日付が古いと思うときは、スキルが案内する公式の料金ページで確かめ、確かめられなかったことを伝えます。
- `claude-api` スキルが使えない、または単価が示されないときは、`--prices` を付けずに進めます。金額なしのレポートになります。
- `prices.json` に入るのは公開の単価だけで、ログの内容は含まれません。

```
python3 <scripts>/tokdiet.py --out ~/tokdiet-out --prices ~/tokdiet-out/prices.json --snapshot ~/tokdiet-out/baseline.json
```

- 既定の入力は `~/.claude/projects` です。特定のプロジェクトだけ見るなら `--root ~/.claude/projects/<proj>` を付けます。
- `--snapshot` は変更前の基準を保存します。`baseline.json` がすでにある場合は、上書きしないよう `--snapshot` を付けず、代わりに `--compare ~/tokdiet-out/baseline.json` を付けて、前回の変更の効果を先に見ます（手順 5 と同じ）。
- 前回の計画や baseline が残っていたら、最初に読みます。前回出した未完了の提案は、同じ結論を一から導き直さず、今も当てはまるかだけを確かめます。

### 2. action-brief.md を読む
`~/tokdiet-out/action-brief.md` を読みます。優先アクション上位 10 と、実測の重い順の上位 5 が入っています。

- 「データ不足」と表示されていたら、提案を作りません。利用を続けてから再実行するよう伝えて終わります。
- 重い順の上位 5 には、提案が立たない項目も載ります。優先アクションにないことは、軽いことを意味しません。

### 3. 根拠を自分で確かめる
各項目に付いた「根拠の再確認コマンド」を実行して、数字が本当にそうなっているかを確かめます。確かめられなかった項目は計画に入れません。

- コマンドは、項目ごとに 1 本ずつ、別の呼び出しで、`action-brief.md` に書かれた形のまま実行します。複数の項目を `for` ループや `&&`、`;` でまとめて 1 回で実行しません。権限の自動判定に、まとめた実行が拒否されることがあるためです。
- 拒否されたら、形を変えて再試行せず、その項目は「確かめられなかった」として計画に入れず、ユーザーに伝えます。実行を許可するかはユーザーが決めます。

### 4. 計画を出して止まる
項目ごとに、次の 4 点を表にして提示します。

| 対象 | 実測 | 変更案 | 確認方法 |
|---|---|---|---|

- 実測の重い順に並べます。重さの単位は項目間で揃っていないので、順位は目安だと添えます。
- 「クイックウィン」と「要検証」を分けます。
- 変更案は、どのファイルのどこを変えるかまで書きます。ほかの設定やスキルから参照されていないかも調べて、影響範囲を添えます。
- 最後に、ユーザーに選んでもらう点（どれをやるか、全体に効く変更かプロジェクト限定か）を挙げます。

**ここで止まります。** ユーザーが項目を選ぶまで、何も変更しません。

### 5. 承認された変更だけ行い、前後を測る
承認された項目だけを変更します。変更の前に手順 1 の `--snapshot` で基準を取っていることを確かめます。数日から 2 週間ほど使ったあとで、次を実行します。

```
python3 <scripts>/tokdiet.py --out ~/tokdiet-out --prices ~/tokdiet-out/prices.json --compare ~/tokdiet-out/baseline.json
```

`action-brief.md` の末尾の「前後比較」を読み、狙った指標が下がったかを見ます。利用量が前後で違うときは、セッションあたりの指標で比べます。下がっていなければ、効かなかったと正直に伝えます。

## 守ること
- 承認なしにファイルを変更しない。
- `action-brief.md` と `baseline.json` は、パス、コマンド、スキル名が入っているので、共有、コミット、Issue への貼り付けをしない。共有してよいのは、匿名の `report.md` / `report.html` だけで、渡す前に次で検査する。

  ```
  python3 <scripts>/leakcheck.py ~/tokdiet-out/report.md ~/tokdiet-out/report.html --logs ~/.claude/projects
  ```

  終了コードが 0 でなければ、渡さずに検出内容を伝える。
- 削減効果の %、円、トークン数を言わない。出せるのは実測した占有量だけ。金額は API 単価での概算で、定額プランでは枠の拡大として説明する。
- 「データ不足」のときは提案しない。
- 品質は測れない。「要検証」の項目は、自分のログで品質が同じかを確かめるまで効果を言えない。同じ入力 3 件を変更前後で流して比べる手順（`action-brief.md` の該当項目に書いてある）を案内する。「品質に影響しない」とは言わない。
- 価格表をスクリプトやリポジトリに書き込まない。単価は実行のたびに `claude-api` スキルから取り、`prices.json` として渡す。
- 最後に、ユーザーへ `report.html` / `report.md` の場所と、レポートの「測れなかった項目」を伝える。
